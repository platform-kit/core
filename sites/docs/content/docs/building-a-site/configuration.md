`platformkit.config.js` is the one place the kit and the theme learn about a site. It exports a plain object. A change to it restarts the dev server. While it runs, the Vite plugin also watches Markdown edits and refreshes only the build steps whose declared inputs match the changed path.

From the Core checkout, a site command reads this config from the selected site. When that site is a separate checkout, the Git-source CLI installs the kit and theme into its `node_modules` from the same Core source, without writing the site's manifest or lockfile. Its receipt checks the files npm actually packs for each package, so development-only files in the Core checkout do not cause a false mismatch. A production host can do the same by running `npx --yes --package=github:platform-kit/core platformkit deploy` from the site checkout; deploying from Core source does not depend on publishing the packages to npm.

```js
export default {
  name: 'Northlight Press',
  theme: 'platformkit/theme',
  modules: { store, print, memberships, sessions, coaching, support, funnels, emails, forms,
             instrument, recommendations, translation, tts, enrichment, push },   // true | false
  looks: { classic: { css: './src/looks/classic.css', skins: './src/components/landing/skins/index.js' } },
  defaultLook: 'classic',
  languages: ['en'],
  overrides: { SiteMark: './src/components/SiteMark.vue' },
  nav: { links: [{ key, href, prefix? }], cta: { href, hrefIn, key, keyIn } },
  routes: [{ path: '/tools', component: './src/pages/Tools.vue', prefix?, prerender? }],
  app: { tabs: './src/instrument/ui/tabs.js' },
  landing: { sections: './src/components/landing/sections.js', schemas: './src/components/landing/schemas.js', stages: './src/components/landing/stages/index.js' },
  analytics: { panels: [{ key, component }], events: [{ key, label, goal?, value? }], sources: [{ key, name, hosts }] },
  api: { space, public },
  instrument: { module: './src/instrument/index.js' },
  recommendations: { module: './src/instrument/recommendations.js' },
  spaces: { deskSources: './src/community/desk-sources.js' },
  admin: { sections: './src/admin/sections.js', models: './build/admin-models.mjs' },
  collections: './velite.site.js',
  enrichment: { briefs: './build/briefs.mjs' },
  data: { schemas: './db/schemas', rows: './db/data.sql', functions: './db/functions', seed: './db/seed.sql', ports: 54320 },
  dev: { projectId: 'pk_northlight_local', projectName: 'Northlight Press' },
  inference: {
    providers: [{
      id: 'primary', protocol: 'openai-chat', secret: 'env:PRIMARY_API_KEY',
      baseUrl: 'https://api.example.com/v1', model: 'example-model',
      models: { 'example-model': { inputPerMillionUsd: 1, outputPerMillionUsd: 2 } },
    }],
    fallback: { enabled: true, maxAttempts: 1 },
    markup: { default: 1.25 },
  },
  usage: {
    autoTopUp: { enabled: true, packKeys: ['0123abcd'] },
    operations: {
      'assistant.game': { mode: 'offer', offerKey: '0123abcd' },
      'assistant.staff': { mode: 'site-funded' },
    },
  },
  payments: { provider: 'stripe' }, // Stripe is the default; see Payment providers for site-owned adapters
  build: { tests: ['./build/results.test.mjs'], steps: ['./build/steps/books-csv.mjs'] },
}
```

## The admin and content store

When a site registers `admin.models` and has a backend, its production content store must be rows. The build resolves the declared shape into the content-store flag before compiling the browser bundle, so both a repository-backed deployment and a Supabase-only deployment include the CMS. A file-backed build for such a site is refused rather than shipping a production admin without its editors. A backend-free static build remains valid and has no deployed CMS or authentication.

In development, Vite also answers `GET /__platformkit/site-meta` for workspace directory previews, using the built site/page/UI records and the shared SEO resolver.

## Inference providers and operation policies

`inference` is the site's private provider and cost declaration. Its `providers` array is ordered,
supports at most four providers, and each entry names an `id`, a supported `protocol`, a `secret`
as `env:UPPERCASE_NAME`, an optional `baseUrl`, a default `model`, and the provider's `models`
with required `inputPerMillionUsd` and `outputPerMillionUsd` rates. Optional rate fields price
additional usage dimensions only when the provider adapter measures them. These rates are the
site's own upstream prices in USD; the same model label at another provider is a different tariff.
The secret value belongs in the deployment environment, never in this file.

`fallback` controls whether configured providers may be tried in order, which HTTP statuses
permit retry, and the maximum number of attempts. `markup.default` is the multiplier applied
after measuring provider cost. `markup.offers` can override it for a stable usage offer key.
Reader-billed model work requires a complete provider tariff and a reservation for the maximum
cost of every permitted attempt before the first external call.

`usage.operations` maps stable, server-selected operation IDs to `{ mode: 'site-funded' }` or
`{ mode: 'offer', offerKey }`. An offer's existing usage declaration selects prepaid or metered
authorization. An operation may set `markup` to override the offer and site defaults; the
precedence is operation, offer, then site. Site-funded work records upstream costs without
charging reader units. Missing operation policies fail closed rather than inheriting another
operation's billing rule. The map is server-only and is not available through `#site`.

## A shop of your own

`store.suppliers` and `store.kinds` are how a site adds to the shop rather than configuring
it. A **supplier** is whoever makes or sends a thing — the kit ships three printers, the
shop’s own post room and a download; a site may add a bindery down the road, a dropshipper,
anything that can answer the interface. A **kind** is a sort of thing to sell whose needs are
its own, reaching the store through two slots and no more.

```js
store: { suppliers: './build/suppliers.mjs' },
```

The registry walks the kit’s and the site’s as one list, and nothing downstream knows which a
supplier came from — which is the only way a seam is real. One that does not keep the shape is
refused by name when it is registered, with what is wrong with it, rather than halfway through
somebody buying something. Each declares the environment keys it `needs`, so a deploy can
refuse before it starts: a sale that fails at the till is finding out too late.

## Two libraries vite must leave alone

The plugin excludes `onnxruntime-web` and `@matrix-org/matrix-sdk-crypto-wasm` from vite's dependency
pre-bundling, and both for the same reason: each finds its own runtime files at run time, relative to
its own module. Pre-bundled, the Matrix crypto library's `.wasm` resolves to a path under
`node_modules/.vite/deps` that the dev server answers with HTML, and `WebAssembly.instantiateStreaming`
refuses it as the wrong MIME type — with nothing else to show that anything is wrong. Left as it is,
the same address is the real file and arrives as `application/wasm`. Importing the file directly
instead is refused: that package's exports map has a single entry.

## Reading the config in code

The kit loads it with `loadSite()` (`packages/kit/build/site.mjs`), which fills defaults, resolves paths, and resolves the [module manifests](/content/docs/building-a-site/modules) — so `site.moduleKeys` is every module that exists and a name outside it is refused rather than read as "on". In the browser the config's public part is `#site`; each registration is its own virtual module (`#site/nav`, `#site/landing`, `#site/app`…) — see [The theme and overrides](/content/docs/building-a-site/the-theme-and-overrides).
