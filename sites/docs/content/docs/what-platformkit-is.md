## What it is

PlatformKit is an open-source toolkit for running a business on one site — the content system, the shop, the subscriptions, the bookings, the community, the support desk, the newsletter and the funnels, the analytics, the search, the page builder — built once, under one roof, with a default theme that covers most of what such a business needs on the day it launches. Somebody adopts it to be in the business of creating and managing, not of building the generic infrastructure underneath.

**What kind of business is a question of which modules are on.** A documentation site, a shop, a subscription business, a practice taking bookings, a community, a course, a publisher, a SaaS product with accounts and plans, a directory built out of content models — and, usually, several of those at once, since a real business is rarely only one of them. The framework knows nothing of any particular trade: what a module deals in is a **record**, a **price**, a **class of person** and an **event**, and every feature is written against those four.

It exists at two levels at once, the way Laravel + Spark is a framework with a working application layer, or WordPress is a framework and a working site the moment it is installed:

- **The framework** (the kit): the machinery every instance runs on, none of it visual.
- **The application** (the modules): working features — a library, a store, memberships, sessions, chats, a support desk, funnels, emails, print, spoken books — each a switch.

You do not build a site _with_ it so much as _configure one out of it_: pick the modules, add content and a palette, register anything of your own. Northlight Press (the demo) and this documentation site are two instances of the same thing, and they have almost nothing in common. Community layout is also a site choice: in the social layout, the configured community home is canonical and bare `/spaces` is its alias, not a second feed.

Its **origin** is publishing, and that shows in the defaults rather than in the framework: the theme ships a library, a chapter allowance, a newsletter. Nothing underneath is about books. The library is one module among a dozen, and it is switched off on this documentation site entirely. A SaaS product with nothing to read, a studio that only takes bookings, a shop that only sells things, a community that sells nothing at all — each is a configuration, not a fork. Its nearest neighbour on the SaaS side is a starter kit like ReadyKit; the difference is that PlatformKit is a running product with a theme, not a starting point.

## How it is opinionated

**Laravel's kind of opinion: convention over configuration, and a small number of strong conventions rather than a large number of options.**

- A site is content in markdown plus one config file.
- Every outside service — payments, the calendar, the printers, mail, push — is made to match the files, never consulted for what the files say.
- Every reader-facing word is markdown, editable in one place; nothing is hardcoded in the interface.
- Structured data is edited as fields, never typed as its grammar.
- A concept with its own lifecycle is its own record.
- Identity is the account; nothing real hangs off a typed claim.
- Nothing unpublished exists outside the admin.
- The interface is looked at before it is shown.
- A deploy that cannot succeed is refused before it starts.

**Batteries included, every battery replaceable.** Each module works out of the box with the default theme, and each can be switched off — or any piece of it overridden by name — without touching the kit. Off means absent: no pages, no menus, no admin views, no build step, and the deploy stops asking for that feature's secrets; a module's heavy packages come with the site that switches it on, not with the kit. The build itself is batteries too: every job it does is a step a site or a theme can add to. Someone who accepts the conventions gets everything working together; someone who fights them will find the kit in the way, on purpose.

Its shape is **WordPress's**, because it is the one every developer already knows: a core, a theme, a site.

## The framework level

- **A config-driven core** — one file declares what an instance is: which modules are on, its looks, its navigation, everything it registers. The framework reshapes itself from it: routes, menus, the admin, the build, the deploy, even which secrets it demands.
- **A content system** — every kind of content is a collection of markdown or JSON files with typed fields, compiled into the app at build time. An instance can add its own collections.
- **Accounts and access** — sign-in, staff roles, and four classes of person (guest, signed in, paying, member) that every feature's rules read. They are the one ladder: what a page shows, what a nav link does, what a chat allows and what an API answers all read the same four.
- **A declared database** — where Laravel or Rails would have migrations, the kit states what the database should look like, instances add their own tables beside it, and a deploy computes and applies the difference — refusing data loss without a human yes for that one run.
- **Serverless functions** — the kit's own for payments, webhooks, mail, chat and print, and room for an instance's.
- **A theme contract** — the visual layer is a separate package with a manifest; any component can be replaced by name, any word overridden, any palette swapped, without forking the theme.
- **An extensible admin** — an editing admin generated from the collections, into which an instance registers its own screens and the handlers behind them.
- **Build, dev and deploy** — one CLI: a dev server with a local stack, a static build with prerendering and share images, a self-checking deploy, a test runner that includes the instance's own tests.
- **Money and mail are mockable** — every buying path, every printer and every email can run locally with no accounts and no cost; the deploy refuses a mock left on.

## What an instance is

A config file, a `content/` folder and a palette — and, optionally, overrides of theme components, its own content collections, routes, admin sections, database tables, functions and tests.

- Everything off but the docs → a Docusaurus-style documentation site, static, with no database.
- The store on and the library off → a shop.
- Memberships, spaces and the support desk on → a paid community.
- Sessions and memberships on → a practice that sells time.
- Content models and the page builder on → a directory or a marketing site for anything at all.
- The store and memberships on over the library → a Ghost-plus-Shopify press.
- Add an instrument of your own → a diagnostic or assessment business.
